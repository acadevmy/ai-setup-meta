# AGENTS.md — Meta-Setup Repository

> This file is the **ground truth** for any AI agent working in this repository.
> Read it end to end before doing anything.

## Identity and purpose

You are the agent responsible for **generating and maintaining** the team's multi-domain
AI-native templates. Your main output is the templates under `templates/` and the content
distributed through `dist/`.

You are not a general-purpose assistant: you are a **specialised maintainer**. Every action
you take must improve the quality, the coherence or the automation of the templates.

## Core operating rules

### Before any change
1. Read the rule templates under `templates/<domain>/rules/` to check which
   constraints the domain declares
2. Check whether a skill under `.claude/skills/` already covers the task
3. Check the state of the current branch — never work directly on `main`

### Branching
- Always create a branch with a descriptive name: `feat/`, `fix/`, `chore/`
- If the task comes from ClickUp, put its customId (e.g. DE-123) in the branch name
- Format: `feat/DE-123-add-user-auth` or `chore/DE-456-update-dependencies`
- For tasks without a customId (e.g. internal maintenance): `chore/sync-constitution-v2`
- Use the `git` and `gh` CLIs to create branches and PRs

### Commits
- Language: **English**
- Format: **Conventional Commits 1.0**, mandatory
  ```
  feat(constitution): add no-any rule for TypeScript
  fix(mcp): correct ClickUp API endpoint
  chore(profiles): update mobile stack to Flutter 3.24
  ```
- Never commit with `--no-verify`

#### Types and their effect on the release

The commit type decides the automatic bump [release-please](https://github.com/googleapis/release-please) computes on the next push to `main`. release-please opens or updates a running "release PR"; merging that PR creates the annotated tag and the GitHub Release.

| Type | Bump | Notes |
|---|---|---|
| `feat:` / `feat(scope):` | minor | New user-visible functionality |
| `fix:` / `fix(scope):` | patch | Bug fix |
| `perf:` / `revert:` | patch | |
| `feat!:` / `fix!:` or `BREAKING CHANGE:` in the body | major | See "Breaking changes" below |
| `docs:` / `style:` / `chore:` / `ci:` / `test:` / `refactor:` / `build:` | no release | They show up in the CHANGELOG but do not bump the version |

To stop an important documentation commit from being ignored, use `feat:` when it introduces functionality (e.g. a new onboarding section).

#### Breaking changes

Either of these two forms:

```
feat(setup)!: drop sonnet model fallback
```

or the explicit footer in the body:

```
feat(setup): switch to opus default

BREAKING CHANGE: setup skill now requires extra usage on Pro plans.
```

Both trigger a major bump on the next release-please run.

#### What lands in the CHANGELOG

release-please **generates CHANGELOG.md from the commits** since the last tag. The commit subject (its first line) becomes the entry. So:

- **Squash-merge is recommended** — the squash commit's subject is the PR subject, which is typically already Conventional-Commits formatted. No noise from intermediate merge commits.
- **Readable subject** — treat the commit subject as release-note-ready. For example: `feat(profile): add Terraform profile with S3 backend recipes`, not `feat(profile): wip`.
- **Informative scope** — `feat(profile)`, `fix(setup)`, and so on. The scope goes into the CHANGELOG, grouped by category.

release-please groups the entries by type (Features / Bug Fixes / Documentation / Performance / …) in the CHANGELOG's `## [X.Y.Z]` section. The `## [Unreleased]` section is not used — release-please derives everything from the commits.

### Pull requests
- Every change to `main` goes through a PR — no exceptions
- The title follows Conventional Commits
- The description must cover: **What changes**, **Why**, **How to test**
- Always add the right label: `constitution` (now the path-scoped rules), `template`,
  `skill`, `profile`, `release`

### What you must never do
- Never change a rule template under `templates/*/rules/` without a human-approved PR
- Never push to `main` directly
- Never put an API key, a token or a secret in any git-tracked file
- Never use `any` in TypeScript, not even in generated configuration files
- Never `force push` a shared branch
- Never read `.env` / `.env.local`: they are denied to the file tools and to the sandbox.
  If a procedure seems to require it, the procedure is wrong — report it instead of working around it
- Never let a token appear on a command line (a push URL, a `curl` header, an `echo`):
  it ends up in `ps aux` and in the logs. Use `gh`/`glab`, which read it from the environment
- Never run `claude` with `--dangerously-skip-permissions` or
  `--permission-mode bypassPermissions`, and never add `permissionMode` to an agent's
  frontmatter: it bypasses the `ask` rules, which are the human checkpoints

## The plugin's scripts and hooks

The deterministic work does not live in prose the model re-interprets on every run:
it lives in scripts the agent calls. Source under
`templates/dev-setup/.claude/scripts/`, shipped to `dist/dev-setup/scripts/` and
reachable at runtime as `${CLAUDE_PLUGIN_ROOT}/scripts/<name>.sh`.

**Script contract** — bash + `jq`, no other runtime dependency · `--json` prints a
flat object with `UPPER_SNAKE` keys · a missing value is the empty string, never a
message · diagnostics and errors on stderr, never on stdout · a failure exits with a
status other than 0.

| Script | Returns |
|---|---|
| `detect-stack.sh` | `LANG`, `FRAMEWORKS`, `PKG_MANAGER`, `VCS`, `MONOREPO`, `HAS_FRONTEND`, `HAS_MOBILE`, `HAS_INFRA`, `SERVICES_GLOB`, `TEST_CMD`, `LINT_CMD`, `TYPECHECK_CMD`, `HOOK_MANAGER` |
| `sdd-start.sh --task DE-123` | `BRANCH`, `REPO_ROOT`, `SPEC_DIR`, `VCS`, `BASE_BRANCH`, `BRANCH_EXISTS`, `CREATED` |
| `check-prerequisites.sh` | `SPEC`, `SPEC_STATUS`, `PLAN`, `CHANGED_FILES`, `AVAILABLE_DOCS`, `BASE_BRANCH`, `MERGE_BASE`, `BRANCH`, `TASK_ID` |
| `render-template.sh --in <file>` | the rendered template; an unresolved `{{PLACEHOLDER}}` is an error |
| `migrate-settings.sh --in <file> --template <file>` | the merged settings, plus `MIGRATED`, `REASON`, `ADDED_SANDBOX`, `ADDED_ASK`, `ADDED_DENY`, `RETIRED_ALLOW`, `KEPT_ALLOW` |
| `common.sh` | sourced by the others: JSON emission, base-branch resolution, slug |

### The UPDATE path is part of the contract

A change to what the setup writes is only half done until UPDATE can carry an
existing project across it. The chain nearly shipped the counter-example: PR 5
added the Bash sandbox to the settings template and verified it on a *fresh*
session, but conflict detection reads an existing `.claude/settings.json` as the
team's file and keeps it — so on every project already set up, the sandbox never
arrived, while `core.md` went on telling each session that "the sandbox denies
reading `.env`". A rule describing a mechanism the project does not have is the
defect this plugin exists to remove, reintroduced through the upgrade path.

`migrate-settings.sh` is the fix and the pattern: the migration is a script with
fixtures in CI, not prose asking the model to perform jq surgery on a file whose
team-added entries must survive. When you change a generated artefact, ask the
three questions — does UPDATE detect the old shape, does it migrate rather than
ask-and-skip, and does a declined migration get reported instead of assumed?

**Never hard-code the base branch.** `check-prerequisites.sh` resolves it from the
repository and returns the fork point as `MERGE_BASE`. Among the candidates (the
upstream, the remote default, `main`/`master`/`develop`/`next`) it picks the one HEAD
forked from most recently. `git diff main...HEAD` is wrong on any project whose work
targets `next` — this repo included: it reports the whole `main..next` delta as part
of the branch.

### The adaptive commit gate

`hooks/gate-commit.sh` is a `PreToolUse` hook on `Bash`. It picks its mode from what
the project already owns, so the checks run once and only once:

- **`HOOK_MANAGER` detected** (husky, lefthook, simple-git-hooks, a custom
  `core.hooksPath`) → **anti-bypass**: the project's own tooling runs the per-commit
  checks, and the hook only refuses the attempts to go around it (`HUSKY=0`,
  `LEFTHOOK=0`, `-c core.hooksPath=…`, `GIT_CONFIG_*`; `--no-verify` and `-n` are
  also `deny` rules in `settings.json`).
- **no hook manager** → **full gate**: it runs `LINT_CMD`, `TYPECHECK_CMD` and
  `TEST_CMD` from `detect-stack.sh` and denies with the tail of the real output as
  the reason.

The bypass scan reads the command with the quoted strings removed, so a commit
*message* mentioning `HUSKY=0` is not treated as an attempt to set it. The full test
suite is deliberately not the per-commit gate: it belongs at the MR boundary and in
CI, which stays the final gate.

The hook is fail-open — no `jq`, no `detect-stack.sh`, and it warns on stderr and
lets the call through. It is a quality gate, not a security boundary: the security
boundary is the `deny` rules plus the sandbox, and blocking every commit on a broken
toolchain would be worse than reporting it.

### Running the tests

```bash
bash scripts/test-plugin-scripts.sh              # the suite
bash scripts/test-plugin-scripts.sh --update     # rewrite the detect-stack snapshots
```

Several tests create git repositories, which a **sandboxed session refuses to do
inside the project** (writes under any `.git/` are blocked there, new repositories
included). The harness probes for a usable directory and, when it cannot find one,
says so: point `TEST_TMPDIR` at a writable path outside the project. In CI, where
there is no sandbox, the repo-local default works.

## The skills: progressive disclosure and public surface

A `SKILL.md` is a routing document, not a manual. The static checks cap it at 500
lines and 500 words; everything past that lives in `reference/*.md` next to it,
read by name and only when the run needs it. Three rules hold the shape:

1. **One hop, no chains.** A reference is linked from its own `SKILL.md` and links
   on to nothing. Check 5 fails a file reachable only through another reference.
2. **A reference over 100 lines opens with an index** (check 6), so a partial read
   is still a useful read.
3. **Cite by name, never with `@path`.** An `@path` force-load injects the file
   into every session, which is the opposite of what a reference is for (check 7).

Contracts more than one skill needs are defined once under
`templates/<domain>/.claude/reference/` and shipped to `dist/<domain>/reference/`.
The skills reach them as `${CLAUDE_PLUGIN_ROOT}/reference/<name>.md`:

| Reference | Holds |
|---|---|
| `clickup-contract.md` | How to call the `clickup` agent: intents, parameters, result format, list-id resolution, the bail-out call |
| `turn-discipline.md` | The rule for an interactive step: after you ask, the turn ends |

**The public surface is four commands** — `setup`, `sdd`, `auto-sdd`, `review`.
Everything else in the chain (`sdd-discovery`, `sdd-spec`, `sdd-plan`, `sdd-dev`,
`verify`, `tdd`, `bdd`, `clickup`, `vcs-ops`) carries `user-invocable: false`: the
orchestrator invokes it by name, and `/help` stays readable. A skill that opens a
PR or writes into a project also carries `disable-model-invocation: true` — a flow
with outward-facing side effects is started by a person, not inferred.

## The governance: path-scoped rules

The domain's rules are not one document a project reads in full at every session.
They are the templates under `templates/<domain>/rules/`, which the setup skill
renders into the project's `.claude/rules/dev-setup-*.md`. The harness injects a
rule when the model touches a file matching its `paths:` frontmatter — a
deterministic match, no re-reading, and it survives compaction.

| Template | `paths:` | Loads |
|---|---|---|
| `core.md` | *(none)* | always — the only unconditional rule, capped at 150 lines |
| `code-style.md` | source extensions, ~28 globs | on any code file, whatever the language |
| `typescript.md` | `**/*.{ts,tsx,mts,cts}` | on a TypeScript file |
| `nestjs.md` | `**/*.{dto,schema,controller,view}.ts` | NestJS projects only, on the files that feed the OpenAPI document |
| `react.md` | `**/*.tsx`, `**/*.jsx` | on a React component |
| `react-native.md` | `**/*.tsx`, `**/*.jsx` | Expo/RN projects only (never generated elsewhere) |
| `vue.md` | `**/*.vue` | on a SFC |
| `flutter.md` | `**/*.dart` | on Dart |
| `dart-analysis.md` | `**/analysis_options.{yaml,yml}` | only when the analyzer config itself is edited |
| `terraform.md` | `**/*.tf`, `**/*.tfvars` | on HCL |
| `tests.md` | `**/*.spec.*`, `**/*.test.*`, … | on a test file |
| `backend-services.md` | `{{SERVICES_GLOB}}` | on the business-logic layer — the glob comes from `detect-stack.sh` |

**What stays in `core.md`.** The line is drawn by consequence, not by topic: a
rule whose absence produces *worse code* can be path-scoped, a rule whose absence
produces an *unsafe or irreversible action* cannot. So secrets, untrusted
content, supply chain and the gates load always; design, error handling and
naming arrive with the file. Git conventions are neither — no glob can predict a
`git commit` — so they live in the `vcs-ops` skill, which loads on the task.

Three rules hold this together:

1. **A rule a machine can check does not live here.** Function length, naming,
   `any`, coverage floors and layer imports are ESLint and the test runner;
   "1 review required" and "no direct push" are branch protection, set by the
   setup's Step 7b. A rule lives in exactly one place, and prose is the place of
   last resort.
2. **`core.md` is the only file with no `paths:`.** Adding a second one doubles
   what every session pays for, everywhere. Check 9 of `/project:validate` fails
   the build if that happens.
3. **The `dev-setup-` prefix is a contract.** The setup regenerates only its own
   files and never touches a rule the project's team added by hand.

To change the governance: edit the template under `templates/<domain>/rules/`,
run `bash scripts/build-plugin.sh <domain>`, and open a PR. Projects pick the
change up on the setup's UPDATE mode.

## Autonomous maintenance pipeline

The meta-repo ships a pipeline that evolves the setup on its own (skills, MCP, profiles,
agents, constitution) by processing dedicated ClickUp tasks and opening review-ready PRs.

### Components
- Orchestrator skill: `.claude/skills/auto-maintain/SKILL.md`
- Subagent: `.claude/agents/clickup.md`
- Quality gate: `/project:validate`
- Boundaries: the `sandbox` block in `.claude/settings.json` (filesystem and network at the
  OS level) and the `deny` rules on force push, direct pushes to the protected branches,
  `--no-verify` and `--dangerously-skip-permissions`. The pipeline runs in auto mode,
  **not** with `--dangerously-skip-permissions` and **not** with `permissionMode: dontAsk`.

> **A note on the sandbox and SSH remotes.** Sandboxed commands reach the network only
> through the HTTP(S) proxy: no raw TCP, no DNS for anything else. With `origin` on
> `git@github.com:...`, a `git push` inside the sandbox cannot even resolve the hostname.
> In the cloud Routine the repo is cloned over HTTPS, so this never comes up; locally you
> either move the remote to HTTPS (`gh auth setup-git` + `git remote set-url`) or the push
> runs outside the sandbox, through the normal permission flow. The `deny` rules hold
> either way: they are permission rules, not sandbox boundaries.

### Flow (per run)
1. Pick the highest-priority SPRINT task from the `CLICKUP_MAINTENANCE_LIST_ID` list
2. Move the task `SPRINT -> IN PROGRESS`
3. Create the branch `chore/<customId>-<slug>` from an up-to-date `main`
4. Classify the kind of change (skill / mcp / profile / agent / constitution / manifest / docs)
5. Apply the changes the task `description` asks for
6. Run `/project:validate`
7. Conventional commit, push, `gh pr create`
8. Move the task `IN PROGRESS -> CODE REVIEW` with the PR link

### Bail-out (on error or ambiguity)
- Task moved to `BLOCKED`
- ClickUp comment with the failed step + suggestions
- The local branch is **not** deleted (for debugging)

### Setup (one-off)

**1. ClickUp connector on claude.ai**

Go to `claude.ai/customize/connectors` and add the ClickUp MCP server:
- **URL**: `https://mcp.clickup.com/mcp`
- **Authentication**: OAuth (follow the flow the interface walks you through)

**2. Environment variables in the Routine**

In the Routine on `claude.ai/code/routines`, set under Environment:
- `CLICKUP_MAINTENANCE_LIST_ID` = `901217493496`
- `GH_TOKEN` = a GitHub Personal Access Token (scopes: `repo`, `workflow`) — `gh` reads it
  from the environment: the pipeline never prints it and never puts it on a command line

**3. Create the Routine**

On `claude.ai/code/routines → New routine`:

| Field | Value |
|---|---|
| **Name** | `auto-maintain ai-base-setup` |
| **Repository** | `acadevmy/ai-setup-meta` |
| **Branch pushes** | Enable *Allow unrestricted branch pushes* |
| **Connectors** | ClickUp (added in step 1) |
| **Schedule** | Daily (or weekdays), at whatever time you prefer |

**Routine prompt** (paste into the Instructions field):

```
You are the maintenance agent for the ai-base-setup meta-repo.

Run the auto-maintain pipeline following exactly the instructions in
`.claude/skills/auto-maintain/SKILL.md`.

The repository is already cloned in this session. Work fully autonomously, with no
interaction, applying the changes the highest-priority ClickUp task in SPRINT asks
for and opening a PR at the end.

Variables available in the Routine environment:
- CLICKUP_MAINTENANCE_LIST_ID: id of the ClickUp maintenance list
- GH_TOKEN: GitHub Personal Access Token for the push and the PR

The ClickUp connector is available with OAuth authentication: use the
`mcp__clickup__*` tools for every ClickUp operation, with no token to handle.
```

**4. Unload launchd (if it was ever installed)**

The local runner (`scripts/auto-maintain-runner.sh`) has been removed: it ran with
`--dangerously-skip-permissions` and `source .env.local`, and the Routine replaces it.
If its launchd entries are still loaded:

```bash
launchctl unload ~/Library/LaunchAgents/com.devmy.ai-base-setup.auto-maintain.plist
launchctl unload ~/Library/LaunchAgents/com.devmy.ai-base-setup.caffeinate.plist
```

**Quick test**: from the Routine's detail page, click **Run now**.

### When a task ends up in `BLOCKED`
1. Read the bail-out comment on ClickUp (step + reason)
2. Open the run's session on `claude.ai/code/routines` to see the full transcript
3. Fix it by hand or reword the task description, then move the task `BLOCKED -> SPRINT`
4. The pipeline picks it up on the next cycle

## CI and automatic gates

Every PR to `main` or `next` (and every push to those branches) goes through five jobs.
They are the repo's safety net: nothing lands on `next` with a red job.

| Job | Workflow | What it checks |
|---|---|---|
| `plugin-validate` | `ci.yml` | `claude plugin validate --strict` on `dist/dev-setup/` and on the marketplace catalogue |
| `shellcheck` | `ci.yml` | Every `*.sh` under `scripts/`, `templates/`, `dist/` at `--severity=warning` |
| `static-checks` | `ci.yml` | `validate-setup-urls.sh` + `validate-plugin.sh --fail-on-stale` |
| `bash-tests` | `ci.yml` | `test-plugin-scripts.sh`: the plugin scripts and hooks against `scripts/fixtures/` |
| `verify` | `build-verify.yml` | `dist/` in sync with `templates/`, `shared/` and the build scripts |

### The baseline of known failures

`scripts/validate-baseline.txt` lists the defects the audit recorded that the static
checks find *today*: they are reported on every run but they do not fail CI. It has
been **empty since DE-16478** — the file stays as the mechanism, not as debt.
There are two rules:

1. **A new finding gets fixed**, not added to the baseline. The baseline shrinks with
   the PRs of the revision chain; it does not grow.
2. **Whoever fixes a defect removes its line** from the baseline in the same PR.
   The `--fail-on-stale` flag turns the CI job red if a line is left orphaned.

The repo's real state, baseline ignored: `bash scripts/validate-plugin.sh --strict`.

## Pre-PR checklist

Before opening a PR, check that:

- [ ] `/project:validate` passes (or the new findings are fixed)
- [ ] The generated files hold no API keys or secrets
- [ ] The template's `CHANGELOG.md` is up to date
- [ ] The stack profiles match the ones in the template
- [ ] `core.md` is still the only rule template without `paths:`, and still under 150 lines
- [ ] Every `SKILL.md` touched is still inside the 500-line / 500-word budget, with a
      `description` that carries a "Use when…" trigger
- [ ] `scripts/validate-baseline.txt` is still empty
- [ ] The template's `manifest.json` matches the files actually present
- [ ] The PR description says how to test
