## Context

The plugin ships four bash hooks (`templates/dev-setup/.claude/hooks/`, mounted through the generated `dist/dev-setup/hooks/hooks.json`). Two of them are mounted on every `Bash` call and decide inside whether the call concerns them: `gate-commit.sh` (`PreToolUse`) runs `jq` and a regex on every command to find a `git commit`, and `post-merge-request.sh` (`PostToolUse`) does the same to find a `gh pr create` / `glab mr create`. Every `ls`, `cat` and `git status` pays for two process spawns and two `jq` parses that end in `exit 0`.

Two of them talk to the model through the wrong channel. `post-merge-request.sh` prints its reminder on stderr and exits 2, and `post-edit.sh` does the same with a formatter's output. On `PostToolUse` exit 2 is the only way stderr reaches the model, so the choice was forced when the hooks were written, and `AGENTS.md` says so ("Exit 2 is the channel and not a verdict"). But the harness renders an exit-2 hook as a `hook error` in the transcript, and the hooks reference now documents the channel that was meant for this: `hookSpecificOutput.additionalContext` on stdout, with exit 0.

Claude Code's hooks reference (`https://code.claude.com/docs/en/hooks`) now documents three things this task adopts or evaluates:

- the handler field `if`, a permission rule (`Bash(git *)`, `Edit(*.ts)`) that decides whether the handler's process spawns at all. One rule per handler, no list syntax ("to apply multiple conditions, define a separate hook handler for each"); it is evaluated on tool events only; leading `VAR=value` assignments are stripped before matching, each subcommand of a compound command is checked, and when the harness cannot narrow a command it runs the hook regardless — the filter is best-effort;
- `additionalContext` in `hookSpecificOutput` on `PostToolUse`, exit 0: the text reaches the model next to the tool result, with no hook-error notice;
- the `UserPromptExpansion` event (fires when a typed slash command expands, matcher on the command name) and the `InstructionsLoaded` event.

The rule syntax is the permissions reference's (`https://code.claude.com/docs/en/permissions`, "Wildcard patterns"): a `*` can go anywhere in the rule and stands in for any text, including none — in `Bash(git * main)` it stands in for the subcommand and every option before it, `-c` included; a trailing ` *` with a space before it also matches the bare command when it is the rule's only wildcard; the space is part of the rule. A subcommand rule does not match a global flag before the subcommand: `Bash(git push *)` does not match `git -C . push origin main`. Before matching, the harness strips a fixed wrapper list — `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob`, bare `xargs` — and `env` is not in it (the list in the 2.1.287 binary is the same).

The task's outcome: the plugin's hooks spawn only on the calls that concern them, and talk to the model through the intended channel, not through `exit 2`. CI pins the CLI at 2.1.295 (`.github/workflows/ci.yml`); `claude plugin validate --strict dist/dev-setup/` runs there on every PR.

## Requirements

- REQ-1: `gate-commit.sh` spawns only on a git commit call. In `templates/dev-setup/.claude/settings.json` the `PreToolUse` group with `matcher: "Bash"` keeps its single `gate-commit.sh` handler (`timeout: 600`) and adds `"if": "Bash(*git *commit*)"`. The generated `dist/dev-setup/hooks/hooks.json` carries exactly this one handler under that group, `if` unchanged. Read with the matcher the permission docs describe (every `*` is any text, including none; leading assignments stripped): `git status`, `git log --format=%H -1`, `npm test` and `echo "about to commit"` do not match; `git commit -m "x"`, `git commit` (bare), `git -c core.hooksPath=/dev/null commit -m "x"`, `git -C dir commit -m "x"`, `HUSKY=0 git commit -m "x"` and `env HUSKY=0 git commit -m "x"` do.
- REQ-1b: every command `is_git_commit` accepts is matched by the `gate-commit.sh` rule — the invariant REQ-1's examples stand for. A shape the hook acts on that the rule does not spawn is a silent failure, and the suite fails on it.
- REQ-2: `post-merge-request.sh` spawns only on a merge-request creation. The `PostToolUse` group with `matcher: "Bash"` holds two handlers for `post-merge-request.sh`, each with its own `if` — `"Bash(*gh pr *create*)"` and `"Bash(*glab mr *create*)"`, one host per handler, because a handler holds exactly one rule — and a command string of its own: the script's path followed by `gh` or `glab`, an argument the script never reads (see the technical decision). The generated `hooks.json` carries exactly these two. `git status`, `gh pr view 12 --json body` and `glab mr list` match neither; `gh pr create --fill`, `gh pr --repo=acme/repo create --fill`, `env GH_REPO=acme/repo gh pr create --fill`, `glab mr create --fill` and `glab mr --repo=g/p create --fill` each match one.
- REQ-2b: every command the merge-request scan accepts is matched by at least one `post-merge-request.sh` rule — the same invariant as REQ-1b.
- REQ-3: Both hooks keep their internal filter, unchanged, so a client that ignores `if` still gets the right decision, and both are asserted in a fixture where an unfiltered hook would speak: fed `git status` in `RED_PROJECT` (staged files, a test script that exits 1 — a gate that reached the checks would deny), `gate-commit.sh` prints nothing on stdout and exits 0; fed `git status`, and the quoted-mention command, with `$MR_URL_GH` in the response and DE-810's clock open (a hook that had not filtered would print the DE-810 reminder), `post-merge-request.sh` prints nothing on stdout and exits 0. The existing assertions that a quoted mention is not the command, and that `git log --format=%H` is not a commit, keep passing.
- REQ-4: `post-merge-request.sh` reports through `additionalContext` and exits 0. When it has something to say (a merge request was created and a clock is open), its stdout is exactly one JSON object `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"<reminder>"}}`, nothing on stderr, exit 0. The reminder text is the one printed today, both variants (one task named; several open and none named), so the existing substrings still hold: `<id> is still IN PROGRESS`, the merge-request URL, `--task <id> --stop --json`, `CODE REVIEW`, `reference/clickup-contract.md`, and for the ambiguous case the list of open ids and `Do not guess`. When it has nothing to say (no merge request created, no open clock, no `jq`, no git directory), stdout is empty and it exits 0, as today. It still does not stop the clock.
- REQ-5: `post-edit.sh` reports through `additionalContext` and exits 0. When prettier or eslint fails on the edited file, its stdout is exactly one JSON object with `hookEventName: "PostToolUse"` and `additionalContext` holding the same text it prints on stderr today (`post-edit: prettier failed on <file>` / `post-edit: eslint reported problems it could not fix in <file>`, followed by the last 40 lines of the tool's output), nothing on stderr, exit 0. When both tools pass, or the file is out of scope, stdout is empty and it exits 0.
- REQ-6: No hook script of the plugin exits 2 any more, in code — comments may still name the old channel. `grep -lE '^[^#]*(^|[^[:alnum:]_])exit[[:space:]]+2([^[:digit:]]|$)' templates/dev-setup/.claude/hooks/*.sh` returns nothing. (`gate-commit.sh` already denies through `permissionDecision` with exit 0; `on-compact.sh` exits 0.)
- REQ-7: The built plugin validates with the `if` keys: `claude plugin validate --strict dist/dev-setup/` exits 0 on the pinned CLI (2.1.295), and `bash scripts/validate-plugin.sh --strict` stays green (checks 14–15 on the edited docs).
- REQ-8: The documentation says what the hooks now do. `AGENTS.md` no longer contains the sentence "Exit 2 is the channel"; its "The adaptive commit gate" section says the hook spawns only on a git commit call (the one `if` rule, `Bash(*git *commit*)`, the hook's own regex in rule syntax) and keeps its own filter for a client that ignores `if`; its "The obligation travels with the event" section says the reminder is `additionalContext` with exit 0 and names the rule: a hook that reports uses `additionalContext`, a hook that refuses uses the `PreToolUse` decision object, and `exit 2` is used nowhere; the footer version is bumped. `docs/developer-guide.md` §5 ("The quality gate on the commit") says the same about `if` in one sentence, naming the rule, and the troubleshooting entry "The merge request is open but the task is still IN PROGRESS" says the reminder arrives as context, not as a hook error. `scripts/test-plugin-scripts.sh` asserts the `AGENTS.md` sentence is gone and `additionalContext` is named there, and that `docs/developer-guide.md` contains `Bash(*git *commit*)` and `additionalContext`.

## Technical decisions

- **One rule, the shape of the hook's own regex.** `is_git_commit` defines a commit as `git`, optional global flags, `commit`, optionally behind `env` and assignments. `Bash(*git *commit*)` is that definition in rule syntax, so it spawns the gate on every form the regex recognises: `git -c core.hooksPath=… commit`, which the task's `Bash(git commit*)` never spawns (the permission docs: a global flag before the subcommand is not matched by a subcommand rule — the smuggled form the anti-bypass mode exists to refuse, `AGENTS.md` "The adaptive commit gate", pinned by the harness), and `env HUSKY=0 git commit`, which no prefix rule spawns, because `env` is not among the wrappers the matcher strips and the gate denies that form today. `git status` contains no `commit` and does not match. The over-spawn (`git log --grep=commit`, `git commit-tree`) is the harmless direction: the hook's regex exits 0. One handler, so nothing rests on how the harness de-duplicates two handlers of one command, which the docs do not describe. `claude plugin validate --strict` accepts the rule: verified in this revision on 2.1.287, on a scratch copy of `dist/dev-setup` carrying the three rules below. *Deviation from the task's `Bash(git commit*)`, forced by the anti-bypass design: a form the hook acts on that the rule does not spawn is the silent failure this plugin cannot absorb.* Listed in `deviations`.
- **The same shape for the merge-request hook, one host per handler.** The scan regex of `post-merge-request.sh` accepts `gh pr create …`, `gh pr --repo=… create`, and the `env` / assignment prefixes. `Bash(*gh pr *create*)` and `Bash(*glab mr *create*)` are that regex in rule syntax; two handlers because a handler holds exactly one rule and the two hosts share no literal — the shape the hooks docs prescribe for two conditions, and what the task itself proposes (two rules). Their command strings differ by a trailing argument the script never reads (`… post-merge-request.sh gh` / `… post-merge-request.sh glab`): the hooks reference deduplicates identical hook commands and does not say whether `if` is part of the key, so two handlers with one command string could collapse into one and the GitLab creation would never spawn the hook — raised in review, pinned by the suite. The over-spawn (`gh pr view --json createdAt`) ends in the hook's own `exit 0`; the mod (`mod/lib/merge-request.ts`) mirrors the *detection*, which is untouched. *Deviation from the task's `Bash(gh pr create*)` / `Bash(glab mr create*)`, on the same grounds as the gate.* Listed in `deviations`.
- **The `if` style is the template's where it costs nothing, and the hook's where it matters.** `settings.json` asks on `Bash(gh pr create*)` / `Bash(glab mr create*)` and denies `Bash(git commit -n*)`, with no space before the `*`; the docs say a trailing ` *` with a space also matches the bare command, so either style would, and the no-space form is kept on consistency with the template's `ask` and `deny` rules alone. The template already relies on the `*<literal>*` shape (`Bash(git commit *--no-verify*)`, `Bash(git push * -f*)` in the deny list); the leading `*` is new to the file, and is what covers the `env` form.
- **The internal filter stays** (the task's Risks, and the docs' "best-effort": a `$(…)` or `$VAR` in the command makes the harness spawn the hook regardless). The `if` saves the spawn on the common path; the hook's regex remains the decision. The `matcher: "Bash"` stays on all three handlers, as in the docs' example.
- **The negatives are asserted where a spawn would show.** The harness's `git status` case for the gate runs in `$SANDBOX`, a repository with no `package.json`, where a real `git commit` fed to the gate prints no decision either ("no quality command detected"); and the quiet cases of `post-merge-request.sh` run before any clock is started, where an unfiltered hook is silent too. Deleting the internal filter would turn nothing red. REQ-3 moves both into fixtures that would speak — `RED_PROJECT` for the gate, the open DE-810 clock for the reminder — so the filter is tested, not assumed.
- **The channel is `additionalContext`, the exit code is 0, stdout holds only the JSON.** The docs: stdout that starts with `{` and ends with `}` is parsed as JSON; stderr on exit 0 goes to the debug log only; exit 2 on `PostToolUse` shows stderr to Claude as a hook error. So the reminder moves to the JSON object, built with `jq -n --arg` (the text holds quotes, newlines and a URL), stderr is left to the diagnostics nobody needs in the transcript (`jq not found`), and the quiet path prints nothing. The reminder's words do not change: the harness, `vcs-ops` and the developer guide all quote them, and the mod mirrors the *detection*, which is untouched — no mod change. The developer no longer sees the reminder as an error notice; the band button the mod adds after a created merge request (DE-17071) is the developer's copy.
- **`post-edit.sh` is in scope, `if` on it is not.** The task's outcome covers "the plugin's hooks" and its notes name `post-edit.sh`; the change is the same four lines as in `post-merge-request.sh`. An `if` on it would need one handler per extension and tool (`Edit(**/*.ts)`, `Write(**/*.ts)`, … — thirteen extensions, two tools), for a hook whose own `case` returns in a millisecond. Not done; one line under Notes.
- **The `if` test is one glob, and the invariant it pins is the hook's.** The harness cannot run the harness's matcher. The permission docs give one rule for these shapes — every `*` is any text, leading assignments stripped — and bash pattern matching (`[[ $command == $glob ]]` on the text between `Bash(` and `)`) *is* that rule: `if_matches` is that one line, not a matcher re-implementation. No rule of the plugin ends in ` *`, so the bare-command special case does not arise, and the proxy says so. What it pins is REQ-1b/REQ-2b: for every shape the hook's own regex accepts — asserted by the hook acting on it in the same test — the rule matches too. It fails if someone narrows the gate rule to `Bash(git commit*)` (the `-c core.hooksPath` form matches nothing) or drops the leading `*` (the `env` form matches nothing). Whether the harness actually skips the spawn is the harness's behaviour, pending in a real session (Notes).
- **`UserPromptExpansion`: nothing to replace on `next`.** `setup-version.sh` and its `case` filter exist only on the unpushed `feat/setup-version-check` branch (commit efd5537), as `.specs/DE-17061-claude-dev-analysis-defects.md` already records. This task touches nothing that is not on `next`. When that branch lands, the right shape is a `UserPromptExpansion` handler with a matcher on the command name (`dev-setup:.*`), and the task's open assumption — whether the event also fires when the model invokes a skill through the `Skill` tool — is answered then, by trying it: the docs say the event covers the typed path. It is not needed here.
- **`InstructionsLoaded` fixture: evaluated, not adopted.** The event fires inside a live session when a rule file loads. The `bash-tests` job runs no session and has no CLI; `mod-tests` runs `claude plugin test` with no session. A test that needs a signed-in `claude -p` run cannot live in CI, and what it would prove — that `dev-setup-*.md` rules carry the right `paths:` — is already pinned by check 9 of `validate-plugin.sh` and the render test in the harness. The gap it would close (the harness's glob matching itself) is the harness's to test, not the plugin's.
- **The builder needs no change.** `build-claude.sh` rewrites the `hooks` block with `jq walk`, touching only strings that match the `$CLAUDE_PROJECT_DIR/.claude/hooks/` path; every other key, `if` included, passes through. The task asks that this be verified: REQ-1 and REQ-2 are asserted on the generated `dist/dev-setup/hooks/hooks.json`, not on the template, so a builder that dropped the key fails the suite. The hard-coded fallback block (used only when the template has no `hooks` block) is left as is: it already lacks `post-merge-request.sh`, and the template has a `hooks` block.
- **UPDATE path.** Hooks reach a project through the plugin's `hooks.json`; the settings the setup writes carry `permissions` and `sandbox` only. Nothing to migrate, as `AGENTS.md` already states for new hooks.
- **Minimum client.** `if` is documented from the 2026-w13 release; CI pins 2.1.295. The docs do not say what an older client does with an unknown handler key; the task's risk assumes it ignores it, and REQ-3 is what makes that assumption safe. → `toConfirm`.
- **Precedence applied.** The project's anti-bypass design and the hooks' own definition of the calls they act on (1) overruled the task's prefix rules (3) for both hooks. The task's outcome (2) — no `exit 2`, hooks spawn only on their calls, `git status` does not start the gate — is delivered in full; its evaluation items (`UserPromptExpansion`, `InstructionsLoaded`) are settled against what is on `next` and what CI can run, and recorded here.

## Notes

- **Pending in a real session**, the way `AGENTS.md` records the mod's pending items: first that the gate spawns on `git commit -m x` at all — a wrong reading of the matcher would leave the gate silently off on every project, with no deny and no notice — then that `git -c … commit` and `env HUSKY=0 git commit` spawn it and `git status` does not, and whether a rule with a leading `*` gets the startup warning the permissions page documents for an *allow* rule with a `*` before the subcommand — nothing says an `if` rule does, and the same throwaway session answers it. `claude --debug` writes every skipped hook to the log with its reason. Not a test the suite can run.
- The task's risk is the design: on a client that ignores `if`, the hooks behave exactly as today, because REQ-3 keeps the internal filter. On a client that *rejects* an unknown handler key the plugin would lose its hooks; the docs give no such behaviour, and the CI pin (2.1.295) is above the 2026-w13 release that introduced `if`.
