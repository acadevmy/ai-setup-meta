## Context

Comparing the `dev-setup` plugin with the current Claude Code documentation (claude.dev analysis, 2026-10-02) found six defects. Each one was re-checked on `next` (03312d4) for this spec:

1. **Version stuck on `next`.** `next` carries `3.3.0` in `.release-please-manifest.json`, `dist/dev-setup/.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` and both `.env.example` files. `origin/main` carries `3.4.2` (releases 3.4.1 and 3.4.2 never came back). The task text quotes `2.3.1`/`3.3.0`, which are older figures; the defect is the same. `git diff --stat next origin/main` touches exactly those five files plus `templates/dev-setup/CHANGELOG.md`. `merge-base(next, origin/main)` is `03312d4`, which is `next` itself, so `next` is an ancestor of `origin/main` and a merge has no conflicts.
2. **`gh pr create` / `glab mr create` stay in the sandbox.** `shared/skills/vcs-ops/reference/github.md:12` uses `--head "$(git branch --show-current)"`, and `gitlab.md:14` uses `--source-branch "$(git branch --show-current)"`. `gitlab.md:15` (short body) passes `--description "<body>"`, where a backtick span in the filled body is a command substitution. `gitlab.md:39-40` suggests `--description "$(cat body.md)"` as a fallback. The settings reference (`sandbox.excludedCommands`) says a command substitution, a subshell, a `cd` or a file redirection keeps the whole call sandboxed. A second fact the task does not mention: **e26cc09 is not on `next` or `main`.** It is the commit that changes `excludedCommands` from `"gh"`/`"glab"` to `"gh *"`/`"glab *"`, and it exists only on the local, unpushed branch `feat/setup-version-check`. On `next` the template still says `"gh"`, `"glab"` (`templates/dev-setup/.claude/settings.json:85`). A pattern with no wildcard is an exact match, so on `next` no `gh pr create` ever leaves the sandbox, whatever its shape.
3. **`userConfig` cannot be read the way the contract says.** `templates/dev-setup/.claude/reference/clickup-contract.md:63` (and `templates/dev-setup/setup/reference/mcp-env.md:35`) name "the plugin's `userConfig`" as the second source of `CLICKUP_SETUP_LIST_ID`. The manifest reference documents two ways a saved value reaches a plugin: `${user_config.KEY}`, substituted in the Markdown body of skills and agents, and `CLAUDE_PLUGIN_OPTION_<KEY>`, exported to hooks. Neither one reaches a Bash command or a file opened with Read. The contract itself is opened with Read, so a placeholder inside it would not be substituted either.
4. **`allowed-tools` in the setup skill blocks nothing.** `templates/dev-setup/setup/SKILL.md:7` declares `allowed-tools: Read, Write, Edit, Bash, Glob, Grep, AskUserQuestion`. The skills documentation says `allowed-tools` pre-approves the listed tools and restricts none. `disallowed-tools` is the field that removes tools, and its effect ends when the user sends the next message. `AGENTS.md:461-463` claims the list "denies the agent launcher and the network". `model: opus` (line 4) is part of the same evaluation. The suite repeats the same misreading: `scripts/test-plugin-scripts.sh:1870-1874` asserts that the setup frontmatter contains `AskUserQuestion`, with the comment "the skill has to be allowed to make them", and today that holds only because of `allowed-tools`.
5. **Commit guidance and a skill named `verify`.** The Claude Code changelog entry, which sits in **2.1.286** and not in 2.1.285 as the task says, reads: "when your *project or user* skills include one named `verify`, Claude is now told to run it right before committing". The plugin ships `dev-setup:verify`, which is neither a project skill nor a user skill. The installed CLI here is 2.1.285, so the behaviour has to be probed on a newer one.
6. **Wrong agent name.** `templates/dev-setup/.claude/skills/review/SKILL.md:34` says "Launch the `review` agent". The agent's frontmatter name is `code-reviewer` (`templates/dev-setup/.claude/agents/review.md:2`).

## Technical decisions

- **The back-merge is the first commit on this run's branch.** A run yields one branch and one merge request. The dev step never pushes and never opens one ("Do not push, do not open a merge request", `templates/dev-setup/.claude/workflows/auto-sdd.js:707`). The launcher pushes the branch `sdd-start.sh` cut from `baseBranch` and opens one MR against it (`run-outcomes.md`, "ready-for-mr"; AGENTS.md: the launcher "is the only side that pushes, opens a merge request or writes to the board"). That overrules the task's "Il punto 1 non passa da una PR di feature … da fare prima degli altri" (precedence 1 over 3), and the acceptance criterion "su `next`, `plugin.json` e il manifest di release-please hanno la stessa versione di `main`" is still delivered (precedence 2). `origin/next` (03312d4) is an ancestor of `origin/main`, so the merge has no conflicts and brings exactly the 3.4.1 and 3.4.2 release commits and their merges. The reviewer chooses how it reaches `next`. One option: merge this MR with a merge commit, not squashed. A squash keeps the 3.4.2 values but drops `main` from `next`'s ancestry, which is what REQ-1's ancestry check catches. The other option: push the merge commit alone as `chore/sync-main-into-next` and merge that first, as #112 (`ba98b0f`, a two-parent merge commit) did, and this MR's diff shrinks to points 2–6. Should a conflict appear anyway, `main`'s side wins on the CHANGELOG and the version files (task, Risks).
- **e26cc09 is brought in by cherry-pick (`git cherry-pick -x e26cc09`).** The acceptance criterion says the create commands "girano fuori dalla sandbox". With the bare `"gh"` entry that is on `next`, they never do, so removing `$(...)` alone delivers nothing anyone can observe. The commit applies cleanly on `next`: `git apply --check` passes, with offsets only. It already carries the UPDATE migration (`RETIRED_EXCLUDED`) and its tests, which answers the AGENTS.md "UPDATE path" question. When `feat/setup-version-check` merges later, the identical patch merges without conflict. This is precedence 2, the acceptance criterion, over the task's assumption that e26cc09 had already landed.
- **Every value is a single-quoted literal, filled from scripts the flow already calls.** `mr-meta.sh` already returns `BRANCH`, `TITLE` and `LABELS` and is already mandatory before every merge request (`vcs-ops/SKILL.md`). The base comes from `sdd-start.sh`/`check-prerequisites.sh` (`BASE_BRANCH`). The reference rows become, for example, `gh pr create --base '<BASE_BRANCH>' --head '<BRANCH>' --title '<TITLE>' --body-file body.md` and `glab mr create --source-branch '<BRANCH>' --target-branch '<BASE_BRANCH>' --title '<TITLE>' --description-file body.md`. Single quotes, never double quotes, for three reasons. Branch names contain parentheses (`sdd-start.sh:118` builds `$BRANCH_TYPE($CONTEXT_SLUG)/…`), and an unquoted `(` is a syntax error. Inside double quotes, a `$` or a backtick span in a filled title or body is a substitution, which keeps the call sandboxed and runs whatever the span holds. And a single-quoted value is inert. Titles can be Italian (`merge-request.md`, `LANGUAGE`), and POSIX single quotes cannot contain a `'`, so both references state that a `'` in a filled value is written `'\''` (`dell'API` → `'dell'\''API'`). The shell variables (`"$BASE"`, `"$LABELS"`) are removed in the same edit. Shell state does not persist between Bash calls, so they were empty by construction. The short-body row becomes `--description '<body>'`. The `glab` fallback for builds without `--description-file` becomes the same `--description '<body>'` form, with the filled body inline. Stdin redirection is not used, because a redirection also keeps the call sandboxed. The "`gh` alone on the command line" bullet that e26cc09 adds to `github.md` gains `$(...)` in its list. The matching `gitlab.md` paragraph loses its pointer to "the `$(cat body.md)` above" and its "expect the unsandboxed retry" sentence, since no form needs `$(…)` any more.
- **The install-time list id lives in the `clickup` skill.** The task allows either the agent or the skill. The skill wins because the value is needed in the main thread *before* any agent call: the flows (`sdd` intake, `multi-sdd` pre-flight, `auto-sdd`) decide whether there is a list at all, and setup Step 6.1/7d needs it but never launches agents. That makes one line in one place, used by every consumer. The contract's resolution becomes: (1) the environment variable; (2) the value the `clickup` skill states, under the label "list configured at install time"; load the skill if it is not in context. An empty value, or one that still shows the unexpanded placeholder, counts as not configured. The documentation does not say what an unset non-required option renders as, so both cases are handled. Nothing else changes: flows still pass `list_id` explicitly to the agent. The line goes into the existing Prerequisites bullet about `list_id` to stay within the 500-word budget (484 now).
- **Setup: `disallowed-tools` instead of `allowed-tools`, and `model: opus` dropped.** This is the documented field that removes tools (precedence 1, what the harness actually does). The setup needs neither the agent launcher nor the web tools. Its network calls (`gh api`, `claude mcp add`) go through Bash under the deny and `ask` rules. The documentation says the removal ends at the next user message, and the setup ends a turn at every question, so the guard covers only the first turn. AGENTS.md is rewritten to say exactly that, and does not claim a boundary. `allowed-tools` goes away: AGENTS.md already treats a declaration that does not restrict as a suspect for the cache re-key, and the only reason AGENTS.md gave for keeping it here ("there the list is real") is false. `model: opus` goes away too, because either reading leads to removal. On the documentation's reading the override lasts only the invoking turn, so a multi-turn setup runs mostly on the session model anyway, and pays two cache re-keys (entering and leaving opus) for the opus part. On the reading in the task and in the project memory ("resta impostato"), it silently moves the rest of the session to opus. The setup's deterministic work is in scripts. Removing the two keys also saves words against the 500-word budget.
- **The existing `AskUserQuestion` assertion is rewritten, not kept beside the new ones.** `scripts/test-plugin-scripts.sh:1870-1874` (added in fbd4468) asserts that the shipped setup frontmatter contains `AskUserQuestion`. Once `allowed-tools` goes, it fails, and its comment states the misreading this task corrects. Its intent is kept: the setup's questions are real `AskUserQuestion` calls (`install.md` alone has three), and they must stay callable. The REQ-5 assertions take its place in the setup section, on the `dist/` copy it already reads, and the comment states the documented rule: `AskUserQuestion` is callable because nothing removes it; `allowed-tools` only pre-approves; `disallowed-tools` is the one field that could take it away, and the docs give exactly that as their example.
- **`verify` is probed first and renamed only on a positive.** The documented wording ("project or user skills") points to "not triggered" for a namespaced plugin skill, so the default outcome is no rename. The task's own Assumption says this has to be verified at runtime. The probe uses a positive control so that a NONE answer means something. If it shows the plugin skill does trigger the guidance, the rename to `spec-verify` follows (task, point 5) and is a breaking change (`feat!`/`BREAKING CHANGE`). No generated project file names the skill (`grep` of `templates/dev-setup/setup`, `rules`, `profiles`), so UPDATE has nothing to migrate either way.
- **Agent references by frontmatter name.** The convention already in use is `spec-verifier` in `verify/SKILL.md:48` and `clickup` in the contract. The new test pins it for every "Launch the `…` agent".
- **Tests live in `scripts/test-plugin-scripts.sh`**, in the grep-assertion style of "the slimmed interactive flow" section (`assert_eq` / `assert_contains`). The meta-repo has no `.claude/rules/`, no ADR directory and no `REGISTRY.md`. The constraints are AGENTS.md and the static checks.
