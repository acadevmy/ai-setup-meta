# Migrating from dev-setup v2 to v3

> This page names things that no longer exist — that is its job. It is the one
> document the docs anti-drift check in CI skips, for exactly that reason.

v3 is the outcome of the revision chain DE-16471 → DE-16488. The single sentence
that explains all of it: **a rule is now a mechanism or it is not a rule.** What
used to be a paragraph asking the model to behave is now a hook that blocks, a
sandbox that denies, a permission rule that asks, a script that exits non-zero,
or a rule file the harness injects when you open a matching file. Most of the
breaking changes below are things that were deleted because a mechanism replaced
them.

## The short version

| | v2 | v3 |
|---|---|---|
| Commands | 11 | 6 |
| Agents | 5 | 2 |
| Governance | one `CONSTITUTION.md`, read in full every session | `.claude/rules/dev-setup-*.md`, injected on a path match |
| Quality gates | prose asking for lint/tests | a `PreToolUse` hook that runs them and denies |
| Merge request | a summary in chat | an `ask` rule on the real command |
| `.env` | a deny rule a Bash command could walk around | an OS-level sandbox deny |
| Unsupervised runs | a 275-line prose skill with three self-approving agents | a workflow script with three adversarial verifiers |
| Build targets | Claude Code, Cursor, Codex, Gemini | Claude Code |

## 1. Commands

**Removed from the public surface.** Eleven commands became six.

| Gone | Replaced by |
|---|---|
| `/dev-setup:tdd`, `/dev-setup:bdd` | Nothing to type. The layer decides the cycle and `dev-setup-tests.md` states it; both cycles live in the `sdd-dev` reference, read by whoever writes the code |
| `/dev-setup:sdd-discovery`, `/dev-setup:sdd-spec`, `/dev-setup:sdd-plan`, `/dev-setup:sdd-dev`, `/dev-setup:verify` | Still there, still doing the same work — but as steps the orchestrator invokes, not as commands. They carry `user-invocable: false`, so `/help` stays readable |
| `/dev-setup:github-ops`, `/dev-setup:gitlab-ops` | One `vcs-ops` skill that reads `git remote` and loads the GitHub or GitLab reference itself |
| `/project:*` in a configured project | Never a real command surface — the plugin has always exposed `/dev-setup:*`. `AGENTS.template.md` documented the wrong prefix, and that is fixed |

**New.**

| New | What it is |
|---|---|
| `/dev-setup:quick` | The fast path: at most three files, no new component, dependency or public interface. Branch → change → commit behind the gate → merge request. No discovery, no spec |
| `/dev-setup:multi-sdd` | Up to five autonomous runs from one session: a sequential pre-flight, then one background run per task in its own worktree |

**Changed.**

- `/dev-setup:auto-sdd` is now a **launcher** for a workflow script, not a prose
  skill. Same entry point, different machine behind it (§2).
- `/dev-setup:sdd` lost four things it charged for on every task: the
  methodology question, the final OK in chat (the `ask` rule on the merge
  request replaces it), a duplicate `simplify` run, and three bookkeeping
  commits. One approval, one commit.
- Every command that opens a merge request or writes into a project now carries
  `disable-model-invocation: true`: a flow with outward-facing side effects is
  started by a person, not inferred.

**Nothing to do on your side** beyond retyping. If you have aliases, scripts or
team docs pointing at a removed command, update them.

## 2. Agents

| Gone | Why |
|---|---|
| `sdd-approver` | It verified that the spec had the sections the template forces it to produce, so approval was guaranteed. A model approving its own output is not a checkpoint |
| `sdd-discovery-responder` | It answered questions generated by the same model from the same sources, and had to mark the only questions that mattered as gray areas anyway |
| `sdd-methodology-picker` | A grep on the spec, deciding something the rules already decide |

What replaced them, in `auto-sdd`: **three adversarial verifiers**, one lens each
— is there a simpler design, is the scope right, is this testable — each told to
*refute* rather than to approve. Two objections stop the run at `needs-human`,
and only a person can clear a lens.

Remaining agents: `review` and `clickup`.

## 3. Governance: CONSTITUTION.md is gone

`templates/dev-setup/CONSTITUTION.md` (621 lines, read in full at every session,
of which roughly half was dead for any single project) is archived under
`docs/legacy/`. It is replaced by path-scoped rule templates rendered into
`.claude/rules/dev-setup-*.md`.

- The harness injects a rule when the model touches a file matching its `paths:`
  frontmatter. Deterministic, free on the sessions that never touch those files,
  and it survives compaction.
- `dev-setup-core.md` is the only file with no `paths:`, and it is capped at 150
  lines. It holds only what is unsafe to discover late: secrets, untrusted
  content, supply chain, the gates.
- Rules a machine can check left prose entirely: function length, naming, `any`
  and coverage floors are ESLint and the test runner; "one review required" and
  "no direct push" are branch protection, which the setup offers to configure.
- Only the rules your stack needs are generated. A Flutter project gets no React
  rule.

**The `dev-setup-` prefix is a contract.** Everything the setup writes into
`.claude/rules/` carries it; everything your team writes there does not. UPDATE
regenerates only the prefixed files, deletes the prefixed ones your stack no
longer needs, and never touches yours.

**If your project still has a `CONSTITUTION.md`**, the UPDATE run tells you it is
superseded, shows what replaced it, and asks before deleting it — a team may
have added its own rules to that file. Answering no leaves it in place, read by
nothing.

The pruning step that used to strip the irrelevant sections is gone with the
document. It is also where the P0.1 bug lived: it pointed at the wrong section
and removed the wrong stack's rules.

## 4. Settings: sandbox, ask rules, deny rules

`.claude/settings.json` grew three things. All of them change what a normal day
feels like, and all of them are deliberate.

**A `sandbox` block.** OS-level isolation for every Bash command (Seatbelt on
macOS, bubblewrap on Linux and WSL2): the `.env` family denied for read and
write, `~/.ssh` / `~/.aws` / `~/.kube` denied, the usual token variables
(`GH_TOKEN`, `GITLAB_TOKEN`, `NPM_TOKEN`, `AWS_*`, …) unset inside sandboxed
commands, and a network allowlist composed from your stack — your package
registry, your forge, and ClickUp if it is configured.

**An `ask` block.** Not blocked, but stopping for you: `gh pr create` /
`glab mr create`, mutating `gh api` / `glab api` calls, and every ClickUp write.
This is where the final OK that used to happen in chat now lives — in front of
the real command instead of a summary of it.

**A completed `deny` block.** Force push in every spelling (`--force` and `-f`),
pushes to `main`/`master`/`next`/`develop`, `git commit -n` and `--no-verify`,
`--dangerously-skip-permissions` and `--permission-mode bypassPermissions`,
`npm`/`pnpm`/`yarn publish`, edits to lock files and to `.git/`.

**The allowlist shrank.** `Bash(node *)`, `Bash(npx *)` and `Bash(claude *)`
were arbitrary code execution wearing an allowlist entry, and they are gone. The
remaining Node entries are narrowed to the package manager your project actually
uses.

### The upgrade path for this file — read this one

Conflict detection reads an existing `.claude/settings.json` as *your* file and
keeps it. On a project configured before the sandbox landed, that would mean
none of the protection ever arrives while `dev-setup-core.md` goes on telling
every session that the sandbox denies reading `.env` — a rule describing a
mechanism the project does not have.

So the setup treats it as a special case:

- A settings.json **with** a `sandbox` key is yours, and conflict detection
  applies.
- One **without** it is an old artefact, and `migrate-settings.sh` merges the
  template into it. Your own allowlist entries survive; the script never writes
  in place, and shows you what it changed before you accept.

If you decline the migration, the summary says plainly that the project is
running without the sandbox and lists what is missing. It does not report a
protection you turned down.

### Credential masking is user-scope

`sandbox.credentials.*` entries with `"mode": "mask"`,
`sandbox.network.tlsTerminate` and `sandbox.network.strictAllowlist` are ignored
when they come from a repository's settings file. Shipping them in the project
template would read as protection and enforce nothing, so they live in
`~/.claude/settings.json` and you install them once.

### SSH remotes

A sandboxed command reaches the network only through the sandbox's HTTP(S)
proxy, so `git push` against a `git@host:` remote cannot resolve the hostname.
The setup asks: switch `origin` to HTTPS (with the forge CLI's credential
helper, so no token lands in a URL), or keep SSH and let git's network commands
run outside the sandbox through the normal permission prompt. The deny rules
hold either way.

## 5. Hooks

| Change | Detail |
|---|---|
| **`protect-files.sh` removed** | It matched `.env` as a substring, so it blocked `.env.example` — which the setup itself has to write — and it only covered Edit and Write, so a `sed` in Bash walked straight around it. The sandbox does the job properly |
| **`gate-commit.sh` added** | `PreToolUse` on `Bash`. **Adaptive**: with a project hook manager (husky, lefthook, simple-git-hooks, a custom `core.hooksPath`) it only refuses the bypasses; without one it runs your lint, typecheck and test commands and denies with the tail of the real output. Fail-open: no `jq`, no gate, and it says so on stderr |
| **`post-edit.sh` scoped** | It used to run `prettier --write` on any file at all, swallow stderr and always exit 0, and it looked for `node_modules/.bin` only at the root, so it was never active in a monorepo |
| **`on-compact.sh` capped** | It used to reinject the whole REGISTRY with no limit |
| **The phantom Stop hook** | Three skills instructed the model to answer `{"ok":true}` to a Stop hook that existed in neither the template nor the built plugin. Those instructions are gone |

## 6. MCP servers are no longer bundled

v2 shipped `mcpServers` in `plugin.json`, so **every** project paid for ClickUp,
Figma and Context7 tool definitions whether or not it used them.

v3 declares none. `/dev-setup:setup` registers only what the project needs:

| Server | Registered when |
|---|---|
| ClickUp | `CLICKUP_SETUP_LIST_ID` is configured — user scope |
| Figma | A frontend or mobile stack is detected — project scope |
| Context7 | Never. The `ctx7` CLI does the same job without paying for tool definitions in every session |

**If you relied on Figma or Context7 being there by default**: re-run
`/dev-setup:setup`, which registers Figma when your stack warrants it, or add
the server yourself with `claude mcp add`. For library documentation, use
`npx ctx7@latest`.

## 7. Cursor, Codex and Gemini support removed

DE-16489. The plugin has one build target: Claude Code.

Removed: `scripts/builders/build-cursor.sh`, `build-codex.sh`,
`build-gemini.sh`, the `.cursor-plugin/` manifest and catalogue,
`dist/dev-setup/commands/` (63 KB of skill bodies duplicated as commands),
`hooks.cursor.json`, and `mcp.json`.

**Nothing that worked is lost.** The Cursor hooks were the Claude Code schema
with one variable renamed — inert outside Claude Code — and the `commands/`
files were literal copies of the skill bodies. The Codex and Gemini builders
were never enabled by the manifest.

**If you work in another editor**: the plugin's skills follow the open
[Agent Skills](https://agentskills.io) standard, so a conforming `SKILL.md` is
readable without conversion. Point your tool at the `SKILL.md` files under
`dist/dev-setup/skills/`, or copy them into your tool's skills directory.

## 8. Boilerplate and profiles

Greenfield projects only — none of this touches an existing project.

- **ESLint 9 flat config.** `.eslintrc.base.json` is replaced by
  `eslint.config.base.mjs`. v2 installed the legacy config alongside
  `npm i eslint@latest`, which is v9, so a greenfield project got a linter that
  could not load its own config.
- **The Jest key is spelled right.** `setupFilesAfterFramework` does not exist;
  it is `setupFilesAfterEnv`.
- **Profiles moved to current versions**, and `@tanstack/react-query` replaces
  the package name that stopped being correct in 2022. Zod is on 4, consistent
  with the rules that use `z.iso.datetime()`.
- **The CI boilerplate runs lint and tests.** It previously ran neither.
- **`revert` is allowed in commitlint** — it was forbidden, and `git revert`
  generates it.
- **The phantom slash commands are gone** from the profiles
  (`/project:new-module`, `/project:new-component` and ten others never
  existed).
- **The Nuxt profile** was orphaned and is removed; Vue and Nuxt projects get
  `dev-setup-vue.md`.

## 9. Base branch resolution

`git diff main...HEAD` was hard-coded in `verify` and `review`. On a repository
whose work targets `next` or `develop`, that reports the whole delta between the
two branches as part of your change — every review started with a list of
unexpected files.

`check-prerequisites.sh` now resolves it: among the candidates (the branch's
upstream, the remote default, `main`/`master`/`develop`/`next`) it picks the one
HEAD forked from most recently, and returns the fork point as `MERGE_BASE`.
Nothing in the plugin names a base branch any more.

Related: `worktree.baseRef` takes only `fresh` or `head`, never a branch name,
so on a project targeting `next` the setup writes `head` and the fork point is
passed explicitly.

Only relevant if you maintain the plugin.

| Gone | Now |
|---|---|
| `.claude/commands/release-plugin.md` | release-please: the bump comes from the conventional commits |
| `.claude/skills/generate-setup`, `update-constitution`, `sync-profiles` | They pointed at an architecture that no longer exists |
| `scripts/auto-maintain-runner.sh` | A cloud Routine. The local runner ran with `--dangerously-skip-permissions` and sourced `.env.local` |
| `docs/onboarding.md` (the pre-plugin version) | Rewritten — it described `dev-setup-template`, `mcp/mcp.json` and `/project:setup` |
| `mcp/mcp.json.example` | MCP is registered by the setup, per project |
| `templates/dev-setup/setup-skill.md` | `templates/dev-setup/setup/SKILL.md` plus six references |

with fixtures, and a CI workflow running both plus `claude plugin validate` and
`shellcheck`.

## How to migrate a project

**1. Update the plugin.**

```
/plugin update dev-setup@acadevmy
```

**2. Commit or stash your work first.** UPDATE rewrites files.

**3. Run the setup.**

```
/dev-setup:setup
```

It detects UPDATE mode from `.claude/settings.json` plus either
`.claude/rules/dev-setup-core.md` or a legacy `CONSTITUTION.md`, and asks before
it starts.

**4. Answer three questions carefully.**

| It asks | Answer |
|---|---|
| Migrate the pre-sandbox `settings.json`? | **Yes**, unless you have a specific reason. Declining leaves the project without the sandbox, and it will say so |
| Delete `CONSTITUTION.md`? | Yes, *after* checking whether your team added rules to it. Anything you want to keep goes into a `.claude/rules/<your-name>.md` of your own first |
| Overwrite `AGENTS.md` / `CLAUDE.md`? | Yes, if you have kept your customisation out of them. If not, copy it somewhere else first |

**5. What is regenerated, and what is not.**

| Regenerated | Left alone |
|---|---|
| `.claude/rules/dev-setup-*.md` — overwritten without asking, and any your stack no longer needs are deleted | `.claude/rules/<anything-else>.md` |
| `AGENTS.md`, `CLAUDE.md` — after asking | Git hooks, ESLint, Prettier, CI config |
| `REGISTRY.md`, `.env.example` — after asking; in UPDATE mode they are yours, not artefacts | Dependencies, lock files, source code, `.env` |
| `.claude/settings.json` — only when it predates the sandbox, and only after you accept the diff | |

One edit happens without asking on a file the setup did not write: the
`.claude/worktrees/` line appended to `.gitignore`. It adds and removes nothing.

**6. Check the sandbox against your own commands.** If `pnpm test` or
`pnpm dev` loads a file the sandbox denies, remove that filename from
`sandbox.filesystem.denyRead` in `.claude/settings.json`. A deny cannot be
re-opened from `.claude/settings.local.json`.

## Post-migration checklist

- [ ] `.claude/rules/dev-setup-core.md` exists, and the other generated rules
      match your stack — no React rule on a Flutter project.
- [ ] Rules your team wrote are still in `.claude/rules/` and still yours.
- [ ] `.claude/settings.json` has a `sandbox` key. If it does not, the migration
      was declined and the project has no sandbox.
- [ ] `.claude/settings.json` has an `ask` block naming `gh pr create` or
      `glab mr create`.
- [ ] The allowlist no longer holds `Bash(node *)`, `Bash(npx *)` or
      `Bash(claude *)`.
- [ ] `.claude/hooks/protect-files.sh` is gone and `.claude/hooks/gate-commit.sh`
      is there.
- [ ] `.worktreeinclude` exists, and `.gitignore` holds `.claude/worktrees/`.
- [ ] `CONSTITUTION.md` is deleted, or you know why you kept it.
- [ ] `AGENTS.md` holds no `{{TODO}}` and no `/project:` command references.
- [ ] The project's test and dev commands still run — the sandbox applies to
      them too.
- [ ] A throwaway commit with a deliberate lint error is denied by the gate.
      That is the one-line proof the whole thing is on.
